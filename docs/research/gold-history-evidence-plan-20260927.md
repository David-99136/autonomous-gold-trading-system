## 下一次唯讀採樣：待審核的實驗，不是排程

先補齊採樣器的離線測試與採樣規格，才向使用者取得當次 Demo 連線授權。
目前沒有安排時間、啟動背景程序或預設批准帳戶存取。

1. 範圍限 Demo GOLD；先核對商品、交易時段與本機時鐘，指定新診斷輸出目錄。
   不讀 Live 憑證，不呼叫任何訂單端點，不共用或修改正式交易資料庫。
2. 建議一次最多 75 分鐘、涵蓋至少一個完整 UTC H1 邊界與其前後 M1/M5 邊界。
   這是待批准的採樣上限，不是統計充分條件或已收棒門檻；時段不合適則停止／另約。
3. 每次固定查詢綁定 request ID、GOLD／解析度、from/to、起訖 UTC 與 monotonic 時間、
   clock estimate、不確定度、接收完成時間、狀態碼及去認證市場回應雜湊。
   原始市場回應保留版本，不保存 session headers／憑證。
4. 用事前列出的邊界採樣表比較「開棒標記」與「收棒標記」兩種假說；bid、ask 分開。
   加入相鄰／重疊／單點固定窗口，明確辨認端點重複、缺失與可能仍形成中的列。
   重讀延遲僅作觀測維度，不被轉成自動接受規則。
5. 報價串流如有缺口或接收延遲，就記為不完整樣本；不可用不完整 tick 集合
   硬證明 REST OHLC 不正確，也不可插值補出高低價。
6. 所有 REST 與其他同帳戶程序共用限流；具體請求上限需依核對後官方限制與既有
   流量決定。429、時鐘失準、斷線、寫入失敗或達時間／請求上限時停止；不高頻重試。
7. 結束只產生品質／時間／修訂報告，永遠不自動產生 `ACCEPTED_FOR_FEED`、清鎖或交易訊號。

## 對 finality 的判斷邊界

不要求用有限樣本「證明永久不修訂」；這在邏輯上做不到。
需要的是明確、可審核的收棒接受政策及修訂後處理：接受哪個版本、何時可用、
什麼情況立即封鎖、如何保留受影響決策、如何重新建立緩衝與核准恢復。
若券商只提供可修訂資料，應如實評估風險與替代方案，而非把永久不可變性當作已證實。
在該政策和證據未獲核准前，維持目前未驗證／禁止以此解鎖的狀態。
